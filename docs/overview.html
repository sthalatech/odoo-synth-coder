odoo-synth

Production-masked Odoo dev environments on AWS · one self-contained CLI pipeline

Prod DB → PII-masked dump → provenance-baked image → isolated Coder workspace (one per GitHub issue)

Audience: IT Head · Architect · PM Compute: Coder workspaces (no standing cluster) Cloud: AWS — ECR · S3 · EC2 Interface: odoo-synth CLI

1What & Why

The problem it solves

  • Dev/test needs realistic data, but prod Odoo DBs are full of PII (partners, employees, payments, chatter).
  • Hand-built dev envs are slow, inconsistent, non-compliant — every dev reinvents the setup.
  • Reviewing code for a specific issue ideally starts from a clean env seeded with the right schema + data.

What odoo-synth delivers

  • A repeatable pipeline that masks a prod Odoo DB into a safe dump.
  • A provenance-baked Odoo image (core + addons + enterprise pinned to a commit).
  • Disposable Coder workspaces — one per issue — running Odoo on the masked dump, with the addons repo live-mounted for editing.
  • Full run history, logs, and profiles persisted to S3 (shared across machines).

2How it works — the 5-stage pipeline

1Profile
profile create --source-dsn …
  • Bind a source Odoo DB (DSN)
  • Pin provenance: core git ref, addons repo, enterprise flag
→ profile YAML (S3-mirrored)
2Discover
profile discover <id>
  • Inspect live DB + addons
  • Detect installed modules, python/apt deps
→ discovery.json folded into profile
3Build
profile build <id>
  • Bake Odoo image: core + addons + enterprise @ pinned ref
  • Provenance-tagged
→ ECR image
4Mask
run mask --profile <id>
  • Greenmask over source DB
  • Rulebook: field → strategy map
  • Neutralize mail/payment
  • Prune to last N days (subset)
→ masked pg_dump in S3
5Env
env create --profile-id …
  • Coder workspace from ECR image + dump
  • Addons repo live-mounted (RW)
  • Odoo ready on :18069
→ dev workspace (per issue)
Stages 1–5 are all driven by the odoo-synth CLI Stages 2·3·4 run as ephemeral Coder runner workspaces — no standing compute

4The masking rulebook (the real deliverable)

What it is

  • A maintained YAML map of which Odoo fields are sensitive, by app area (core, accounting, HR, messaging, sales…).
  • Each field is assigned a masking strategy from a fixed vocabulary (fake_*, redact_freetext, null, preserve…).
  • Engine = Greenmask's anon extension; odoo-synth owns the map, not the engine.
  • Pruning — a reduced record set, not the whole DB. A per-profile subset_days knob keeps only the last N days of high-volume transactional tables (sales, invoices, stock, POS, mail…); master data (partners, products, journals) is retained. Done post-restore via a generic FK-cascading DELETE + orphan sweep, because Greenmask's dump-time subset engine can't handle Odoo's cyclic schema.

How leakage is closed

  • Pattern backstop — column-name regex rules catch Odoo's denormalized *_display_name / cache columns across 876+ models (the #1 leak surface).
  • Free-text redaction for chatter/mail/cache fields that can hold a person OR company name.
  • System secrets neutralized — API keys, SMTP creds, payment providers, mail/fetchmail toggled off.
  • Module-metadata scrub — org-name leaks in ir.module.module.author + report templates.

5What is achieved

For the business

  • Compliance — no PII leaves prod; devs work on masked data.
  • Reproducibility — every env is a pinned image + a known dump; identical across devs.
  • Speed — a new dev workspace for an issue is a one-command launch, not a half-day setup.
  • Auditability — runs + logs + profiles in S3, replayable via the CLI.

For engineering

  • Zero standing compute — legacy ECS/Fargate removed; Coder workspaces spin up/down on demand.
  • One config source of truth (config.yaml) — no duplication, secrets delegated to env/SSM.
  • One CLI is the whole UI — no web server to host/maintain; Coder dashboard for workspace launch.
  • Provenance pinned — core + addons + enterprise @ exact commit, so restored schema matches running code.
